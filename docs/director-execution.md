# 从导演意图到执行证据

## 2026-11-01：规划进度也是正式流程的一部分

目标用户仍是希望从主题获得完整视频的创作者。一次长流程遇到本地中断时，已经完成的身份和分镜不应被迫重新抽样，否则会丢失已有创作选择，增加成本和跨镜漂移。维护者也需要区分“还没开始”“结果已返回”“请求结果不明”，而不是从诊断文件名猜测执行状态。

可复现的原行为是：第一镜完成后中断，`--resume` 因为还没有完整 `storyboard.json` 而报错。现有生成阶段的恢复能力没有覆盖前面的创作阶段。本次采用 [Temporal 的执行历史与回放思路](https://docs.temporal.io/workflow-execution)和 [Ninja 对依赖及命令输入的校验思路](https://ninja-build.org/manual.html)，只增加本地规划记录，不引入运行平台、队列、自动重试或多代理框架。

新工作区的 `planning_checkpoint.json` 按顺序记录意图、故事身份和每镜响应。输入指纹绑定上下文、模型及生成参数；意图解释器内嵌提示的源文件摘要也参与绑定。请求前原子写入 started，完整结果返回后写入 returned 与内容摘要。恢复复用已返回步骤，继续执行尚未开始的步骤；failed 和 started 不自动重发，响应丢失与中断不得视为“没调用”。记录整体摘要覆盖顺序与条目，删除条目不能被误判为新的工作。摘要用于完整性校验，不是对可任意改写本机文件的攻击者的密码学认证。

所有复用数据重新经过现有类型、编译、就绪和独立语义审查；错误的稿件仍然报错。returned 只表示调用结果已保存，不表示分镜或成片已通过。旧非事件路径按完整初稿/原有纠错步骤保存，步骤内部中断不猜测补齐；没有新增纠错轮次。已存在正式分镜或镜头账本的工作区继续走原有恢复路径，丢失分镜不能重新规划覆盖；旧诊断记录不会被自动“升级”为检查点。

这是恢复能力，不是提高模型创作准确率的证据。原文的重复输出、语义矛盾和真实坏片均不因此获得通过。主要取舍是增加一个有界的本地状态文件，使用现有原子写入和锁来换取跨进程恢复；不改变分镜内容、规划时长、角色身份、生成模型或验收阈值。

验证覆盖中断后续写、未知结果/异常停止、落盘前后故障、模型/Schema 变更、删除或修改记录、符号链接、重复恢复和并发；并通过离线服务替身跑到真实 FFmpeg 拼接与最终文件导出。测试产物是合成媒体，不能当作真实电影效果。结果见 `output/planning_checkpoint_audit_20261101/REPORT.md`。

## 2026-11-01：流式接收与无歧义 JSON 边界

本次正式纯规划试验 `output/20261101_021739_192672` 使用原有文本模型，Fast 配置不变，`plan_only=True`、视频预算为 0。意图和身份规划完成，首镜响应在 16,384 个输出 token 处截断，原文 50,185 字符，其中同一个空 `target` 字段连续出现 4,013 次。未得到完整分镜，也未进入语义审查或视频提交。现有证据能证明输出退化，不能确定提供方内部为何产生循环。

主要用户是希望自动得到可执行规划的创作者，维护者需要可追溯的失败记录。本次可验证目标是及时停止已经不可接受的响应，并保证重复字段不能静默覆盖已有值；这不等于规划成功。原先的全量缓冲等到模型耗尽上限，随后把循环误报为普通容量不足；标准 JSON 解析还会接受最后一个同名字段，可能覆盖否定判断。单纯加 token、删字段或重新抽样不能解决这个边界问题。

共享分镜调用的严格 Schema 路径改为流式接收。`structured_response.py` 按容器、字符串及转义边界识别同一对象的重复键，立即关闭 SDK 响应；相邻对象的同名键和相同文本值合法。接收到的原文通过已有诊断回调保存，失败标为 `protocol_error` 或 `transport_error`，不改写、不去重、不重新调用。正常响应仍走现有解析、类型、就绪和语义审查。最终 JSON 解析也拒绝重复字段，覆盖旧的 Markdown 包裹输入；重复键错误不进入旧 JSON 语法修复。

取舍是增加一个小型增量词法检查模块，不增加依赖、题材规则、模型或输出上限；完整 JSON 语法仍由标准库判定。流缺少结束状态、拒绝、截断和断连不会被视为成功。关闭客户端响应并不证明服务端已停止计费；本次没有在线测量流式兼容性或取消计费行为。采用 [RFC 8259 对对象键唯一性与互操作性的说明](https://www.rfc-editor.org/rfc/rfc8259.html#section-4)作为边界依据，项目明确拒绝有歧义的重复键。

正式创作客户端另显式设置 `max_retries=0`，与已有审查客户端一致。离线 HTTP 实验证明原 SDK 默认在 429/500 后分别发起三次请求，修复后各一次；这是传输层重试的唯一所有权问题，不通过换模型或重抽创作结果解决。Schema 本身通过标准校验，本次原文的第一项完整入场动作也符合原 Schema；退化处的空 target 合法且可省略，因此没有据此删改创作字段。

离线验证使用本次原始响应、任意分块/转义/嵌套、SDK 的实际 SSE 解码与关闭、正式 plan-only 入口，以及既有正常创作和审查流程。失败样本必须仍然失败，不能通过截断、补分镜或人工判定变成成功。报告见 `output/structured_response_audit_20261101/REPORT.md`。真实规划稳定性和最终视频质量仍未通过验收。

## 2026-11-01：区分角色身份与动作参与对象

真实失败 `output/20261101_015431_580232` 发生在视频提交前：第二段用瓦片作直接接触目标，但编译器只从角色名单生成必需可见对象，漏掉了非人物目标。问题不在于瓦片这个名称，也不是所有场景细节都应该变成验收义务，而是“身份参考对象”和“动作画面参与对象”被错误地当作同一个集合。

`action_authoring.py` 现在从原有动作单元直接生成两种投影：人物仍进入 `characters`，全部注册的交互目标进入 `required_visible_entities`。未使用的道具和可选环境变化不自动升级为强制可见主体。事件几何使用作者已有的 `blocking.frame_position` 或 `camera.screen_positions`；没有位置时保持未指定，不能把作用区域猜成画面坐标。没有修改动作文本、时间、结果必要性、语义判定或旧工作区加载规则。

借鉴材料是 [ZeroLu 的动作与摄影案例](https://github.com/ZeroLu/awesome-seedance#1-cinematic-film-styles)、[LearnPrompt 的参考用途分离](https://github.com/LearnPrompt/awesome-seedance/blob/main/docs/templates/en/character-reference-lock.md)与[时间线状态交接](https://github.com/LearnPrompt/awesome-seedance/blob/main/docs/templates/en/timeline-shot-script.md)。它们是案例和方法参考，不是 Fast 提供方合同或成功率证据；其中其他模型版本的经验不能直接视为本项目的能力。未复制代码、安装技能或引入其自动重试建议。

跨行业参照 [OpenUSD 的场景与资产组织](https://openusd.org/release/intro.html)：多种应用消费同一场景对象，按用途投影而不混淆资产类别。这里只采用职责划分，不引入 USD、3D 引擎或新平台。主要用户仍是输入主题的创作者；维护者可以从不可变原稿追溯人物、道具、可见性及调用边界。

测试以真实三段原稿、开门、面板操作、包裹翻转和乐器演奏覆盖人—物交互；正式离线链路检验 Fast SDK 请求、审查、续拍、FFmpeg 拼接及完成复用。原稿中的语义矛盾不会因编译通过而被认可，否定审查仍阻止视频阶段。完整记录见 `output/scene_target_audit_20261101/REPORT.md`。

## 2026-11-01：用户结果与创作实现的职责分离

主要用户是希望输入主题就得到符合要求视频的创作者，次要用户是维护和恢复任务的人。可观察目标是用户明确结局不被故事概要弱化，且审查批准可以追溯到实际结果文字。范围限定为现有事件创作与规划审查，不引入新的平台、重试或题材词表。

原始试验 `20261101_114005_425790` 的意图与槽位都保留了击杀要求，但身份/故事设定响应已将结局改为点穴失去战力。这个较弱目标随后进入每镜上下文，最终审查又用整体肯定判断放行。因此问题既在创作入口的结果归属，也在审查证据；不是需求传递时丢失，更不是缺少某个武侠关键词。

借鉴 [NASA 产品验证](https://www.nasa.gov/reference/5-4-product-validation/)区分实现符合设计与满足用户预期的做法：明确要求属于用户，编舞、运镜和表现手段属于创作。对新事件创作，故事设定的 resolution 由已验证的用户结局原文绑定到响应 Schema，本地同步校验；无明确结局时仍允许自由创作。不修改原始模型输出来凑通过。

新最终规划审查使用 `requested-outcome-v1`，在原有一次审查中把单个布尔值替换为“证据足以证明／相矛盾／证据不足”的判断与原文引用。证据目录只包括末镜实际结果和结束状态，不包括用户要求、生产槽位或故事概要，防止目标充当自身证据。不要求画面文字重复需求关键词；间接表演也可构成证据，但判断仍有模型不确定性。

非最终批次保留原有前提检查。新缓存保存协议标记、原始响应、需求与证据；旧缓存继续按旧指纹和旧协议读取，不迁移或隐式重新调用。程序将新判断映射回既有验收结构，生成、续镜与视觉验收继续消费同一动作合同。没有增加模型调用次数，也没有更改 Fast 配置。

离线验证覆盖真实身份响应提前拒绝、无证据整体批准拒绝、空证据、不确定与否定结论、引用范围、篡改缓存、跨批、非武打需求、正式规划与恢复、下游提示与视觉合同。历史原稿仍用于无损编译回归；不能把不符合新请求合同的历史响应伪装成新服务响应。完整结果见 `output/requested_outcome_audit_20261101/REPORT.md`。这项改动不是最终视频或模型理解准确率的验收证明。

## 2026-11-01：真实纯规划试验与衔接引用协议

正式入口 `main.py --plan-only --paid-take-budget 0 --take-policy single_pass` 沿用配置，文本模型为 `doubao-seed-2.1-lite`，视频模型仍为 Fast，默认 480p、16:9。工作区 `output/20261101_114005_425790` 完成意图、身份、三镜各 5 秒的创作与结构编译，随后独立审查失败；未进入场景绑定或视频提交，没有自动重试。

原始审查把解释与 JSON Pointer 混写，将第三镜编号误作数组下标，并指向整个 `start_state` 对象而非文字。可证伪诊断结果：这份原始响应符合旧的提供方 Schema，却违反本地消费者合同。自由字符串同时承担解释、需求引用和衔接地址，才是本次可复现的协议缺口，不是字符长度不足。

新协议 `planning-semantics-v7-bound-citations` 保留原有判断结构。程序从同镜后续动作、后续镜头状态和跨批紧邻镜头构造可读原文目录，并按每个动作提供合法路径选项。条件对象 Schema 与本地解码使用同一目录；`basis=continuity` 的地址只能从该动作的后续来源中选择，解释仍写入已有 `reason`。不能指向当前或过去动作、整个对象、文件、网址，也不猜测或修补模型返回值。是否构成必要依赖仍由审查判断，地址合法不等于内容正确。

范围是所有题材的既有审查边界，不新增模型调用、重试或依赖。旧 v6 和未版本化缓存按原指纹和原校验读取，无效记录继续失败。验证覆盖原样失败回放、实际 SDK 请求结构、跨批边界、重复恢复、负面结论，以及物品交接、舞伴旋转和日常动作的来源绑定。

另一项独立问题仍未解决：第三镜写“点穴后失去战力、无力滑坐”，审查却将其判为满足原要求的击杀。修复引用不能据此宣布完整规划通过。保留原稿和肯定判断作为真实反例，另用明确标注的离线否定判断验证阻断路径；不修改原始判定、不用死亡关键词规则替代语义判断。详细证据与验证结果见 `output/planning_citation_audit_20261101/REPORT.md`。

## 2026-11-01：由程序绑定审查对象，模型只返回判断

主要用户是从主题生成连续短片的创作者，次要用户是需要诊断失败、恢复任务而不重复付费的维护者。本次范围限定在现有规划审查边界，目标是让创作内容被准确对应和消费；不增加审查轮次、题材规则或视频重试。

真实记录 `output/20261101_012755_711312` 有两类独立问题：三个无候选结果的单元合法省略了结果审定，但消费者无条件校验；八个交互单元把来源路径写成了整句文本，最后一个还多出一项。放宽长度或只补空值不能解决对象对应关系。原始响应已按原值和 SHA-256 固定为 `tests/fixtures/real_planning_review_binding_failure.json`，没有修改历史任务。

新协议 `planning-semantics-v6-bound-targets` 在请求前根据原稿生成固定审查对象。响应的 `units` 以及结果 `decisions` 都使用固定键；返回 Schema 明确每项适用范围，程序再还原既有内部判定结构。模型负责必要性、证据和语义，程序负责关联关系与完整性。没有候选结果意味着该项不适用；有候选结果却缺少判断则是未完成，必须停止。所有单元仍需原因和分类判断，全片仍需连续性与原需求检查。没有按文字相似度找来源、合并陈述或填充肯定结论。

跨行业借鉴的是[医疗数据对 unknown 与 not-applicable 的区分](https://terminology.hl7.org/CodeSystem-data-absent-reason.html)，以及数据系统中先绑定对象再写入值的职责分离。这里只采用缺失值语义，不引入医疗协议。实现使用现有 Pydantic 和 JSON Schema；[条件 Schema](https://json-schema.org/understanding-json-schema/reference/conditionals)提供设计参照，实际发送的是根据已知原稿编译出的明确对象结构，不依赖提供方支持动态条件关键词。

缓存保存原始服务响应与协议版本，包括无效和否定响应；恢复不隐式重试。旧缓存仍按旧请求指纹读取并验证，不迁移、不重写。这次真实记录仍因错误来源被拒绝，新协议测试通过不等于旧记录被批准。

独立验证覆盖真实原稿、缺项/多项/自由文本来源、否定判断、相同文本不同来源、实际 SDK HTTP 请求结构、缓存复用和分批中断。其他题材通过既有正式流程测试。外部服务响应是显式合成数据，网络被隔离；它们证明协议与恢复行为，不证明模型判断准确率或电影质感。详细结果见 `output/planning_protocol_audit_20261101/REPORT.md`。

## 2026-10-31：需求边界与观察不足收尾

本轮只处理已复现的交付问题：入口把长时长截到 120 秒，计划器又把十镜之外的时长截到 150 秒；明确段数没有进入冻结意图；身份/连续性返回 `null` 会被默认成通过，部分观察不足触发格式重试；指定的验收参考丢失后被忽略，人物审查还只取前两个人。这些都是输入、证据和恢复边界的问题，不需要扩建建模系统。

新计划版本 `production-plan-v8-request-shape` 接收有原文依据的 `requested_duration_seconds`、`requested_shot_count`。自然语言正式入口以语义解释的全片时长为准，避免把“每段几秒”当成总时长；结构化调用的时长与冻结需求冲突则报错。当前计划范围是 4–600 秒整数，每个独立生成段 4–15 秒。指定段数不能满足时长时直接停止，不自行增段或缩短。未指定段数仍用有界默认分配，不声称默认等分本身能实现电影级剪辑。旧版本按原算法恢复，历史分镜不迁移。

为使长计划通过同一审查链，新版超过 24 个动作单元的方案复用原审查器按完整镜头分批；每批保留全片需求、角色、原计划和上批最后一镜，并明确是否为最后一批。接缝失败即停止，最后一批承担完整结局检查。批次缓存绑定整稿与模型，恢复时不重复检查已完成批次，失败记录不会被重试覆盖。根目录 `planning_semantic_review.json` 指向逐批审查和原文证据。离线正式入口已验证 600 秒、40 镜、320 个动作单元，恢复不重新创作或重复审查；未生成 600 秒真实视频。

视觉验收协议更新为 `continuity-v22-observable-evidence`：布尔观察可返回 `true`（证据支持）、`false`（可见违反）或 `null`（遮挡、模糊、采样不足等无法判断）。显式未知不会默认通过，也不会要求模型改成真假；保存 `.evidence.json` 后暂停，生成器保留原任务和原片，不标记为失败原片或发起视频重拍。漏掉必填身份/连续性字段属于协议错误，仍受既有一次结构修复上限约束，不能靠默认值放行。新评审版本不复用旧评审协议的缓存判断，旧文件不批量改写。

指定的尾帧或身份参考缺失时，评审在调用模型前停止。身份图在评审请求中逐一绑定人物 ID，缓存也包含该绑定，换绑不能复用旧判断；有参考的可见人物不再被截为前两人。生成来源记录 `identity_bindings` 仅列实际以 `reference_image` 提交的身份图，同场景 `first_frame` 仍只表示状态交接。没有增加自动制图、上传平台或未经验证的混合输入模式。真实身份稳定性与动作观感仍需实际素材评估。

## 2026-10-31：全片节奏与提交机会

离线审计确认了两个通用设计问题：密集节奏被误设为每个镜头相同比例，挤压入场和结果确认；总提交上限虽然有效，却允许首镜重拍耗尽其他镜头的首次额度。这些问题属于规划范围与资源分配，不用场景关键词、手改分镜或新增真实生成来修复。

新 `production-plan-v7-film-rhythm` 仅对密集、自由编舞计划，把原先各镜头最低交互秒数之和保留为全片预算。当前默认仍为计划时长的 70%，这是项目的既有密度策略，不代表用户逐字指定的阈值，也不宣称它是通用电影美学标准。创作按实际任务配置相对权重，每镜获知已用预算和剩余需求，编译器生成时间轴。总量不足、剩余容量不足或缺失独立结果合同，都在生成前停止。非密集需求、精确动作、动作参考和历史版本保持原行为；本轮不改变自动镜头数量分配。

逐镜通过不等于全片通过。导出前按已接受原片的 SHA-256、实际合同指纹、原始事件观察、采样时间和真实媒体时长重新累计全片交互上下界；重叠区间不重复计算，最终裁掉的片尾不计入，结果确认时间必须在剪辑范围内。缺失证据、重复原片、合同不匹配、下界未达标或阈值不确定均停止导出并保留素材，不会自动重拍或拼成“合格”成片。报告写入工作区 `film_rhythm_review.json`，历史失败记录不迁移、不改判。

正式新建入口默认 `completion_first`：有限总额度中，先为尚未提交的镜头保留一次机会，多余额度才可用于重拍。总额度不足以覆盖首次提交时，在第一次视频提交前停止；这不保证各镜头一定生成成功。命令行可指定 `--take-policy single_pass`，每镜最多一次实际提交；网页创建 API 同样支持 `take_policy`。策略与额度一同冻结，恢复不能重置。未发出的预留可以释放；提交结果未知时仍占用额度，先恢复原任务。旧工作区缺少该字段时保留 `legacy` 行为。

本次验证只使用本地响应替身和合成媒体，包括不同题材/时长的规划、低密度入场与高密度发展组合、证据篡改反例、片尾裁剪、并发恢复、真实生成器重拍边界，以及正式规划到真实 FFmpeg 三段拼接。它验证工程行为；真实人物一致性、动作表现和电影质感仍需有限的真实验收，不能由这些测试推定通过。保持用户 Fast 配置，不新增付费生成。

## 2026-10-29：真实失败后的结果与证据边界修正

正式 Fast 试验 `output/20261029_171222_838382` 提交了两条首镜视频，均被拒绝；后两镜未生成，没有成片。真实记录暴露了两种系统问题：自由编舞仍把“刺向手腕、侧身退步”等自选路线写进必达结果；稀疏采样给出的 3.488 秒又被当成精确值与 3.5 秒比较。原片还显示入场占比较大，因此不能把系统问题修正解释为影片已合格。

新正式自由编舞创作要求每个交互提供 `outcomes: [{entity, state}]`，与 `action/result` 中所选的执行方式分开。程序校验实体归属、目标覆盖和重复；独立规划审查必须引用 outcomes 并明确判断状态是否完整、是否混入自选招式路径、是否满足用户要求。缺失判断、混入路线或只有威胁没有反应都不能进入付费阶段。文本状态的语义仍由模型审查，不宣称类型系统能证明自然语言正确。

仅完整具有独立结果的新自由编舞启用 `performance-v2-outcomes`。共享动作编译器将原始招式留给生成，把每个参与者、反应类型、范围和状态结果投影给验收；续拍冻结这些结果，允许改变进入路径。安全提示同样保留全部事件和结果。原始用户要求、最终结局、人物、空间、运镜与跨镜检查仍独立生效。exact、动作参考和已保存的旧任务不隐式迁移；原来的失败证据不会自动升级为通过。

新验收按实际媒体时长均匀取样（每秒约 4 帧、最多 64 帧），要求事件内逐段报告连续交互区间，排除入场、停顿、摆姿和运镜。局部程序根据真实采样间隔计算时长上下界；跨事件重叠只算一次。只有下界达标才通过，上界仍不足才确认时长失败；跨阈值则报告证据不足，保存原片、采样来源和原始响应，不触发付费重拍。provider 的帧尾补齐用实际媒体时长处理，最低交互时长仍来自冻结计划。

这些上下界描述采样分辨率，**不是视觉模型可靠性的置信区间**。视觉模型仍可能漏看、误认或把准备动作当成交互；需要真实素材和独立观察检验。区间不确定时当前流程停止验收，不承诺自动修复视觉判断。这个取舍优先避免因测量不足重复花费，且不降低作品的通过标准。

离线验证包含两条真实失败记录原样回放、新协议的正式自然语言规划与恢复、普通/安全提示、跨段续拍、语义缓存、媒体补帧、非法区间、区间内部停顿、身份/结局反例，以及搬运/喷涂/区域作用/间接传动场景。通过例是显式测试标注和 SDK 替身，不是真实视频质量认证。旧合同指纹的 `null` 字段回归已通过保留旧规范化行为修复，没有重写历史绑定。最终测试结果记录在任务交付和 `output/outcome-validation-fast.xml`。

最终验证：保持 `doubao-seedance-2.0-fast` 配置运行全量测试，**1200 项通过**（146.36 秒，70091 条既有环境/弃用警告）；`compileall`、`git diff --check` 通过。测试未调用真实生成服务。本轮没有新增付费提交。

## 2026-10-29：上一版制作意图、执行与验收分层（历史）

本轮目标是让正式流程能容纳合理的动作表现变化，同时保住身份、因果、用户要求和可恢复性。事实是上一轮三段制作停在首镜，两条真实 Take 都未通过；当前流水线把导演自行编写的每个微观动作路径与绝对时间窗全部作为硬义务，续拍又只能调整 transition。新的假设是：将表现自由与物理结果分开，能够减少无谓的精确复现要求；离线验证只能证明机制，不能证明真实生成成功率提高。

新生产计划 v6 保存 `choreography=exact/flexible` 和原始需求。要求逐步复现、指定动作顺序或动作参考时走 exact；允许导演编舞时可以走 flexible，旧稿缺省仍 exact。表现模式保留每个事件的参与者、作用、反应类型、范围与可见状态变化；允许不同的具体路径和节奏，不允许把中间动作全部省掉。普通生成和安全重编译共用此投影，不再要求模型在系统推算的精确秒点执行。

验收要求实际观察到的起始、作用、反应和结束时间，检查有限数值、因果顺序、镜头边界、交互时间并集与结果保持时间。重复计算重叠、拿计划时间冒充观察、最终摆姿替代过程都不能通过。`creative_brief_valid` 独立检查本镜应承担的原始要求；人物一致性、空间、运镜与跨镜边界检查继续保留。旧记录不会补入新字段导致指纹漂移；真实失败证据缺少新的观察事实时不能升级为通过。

续拍对 flexible 镜头开放首个交互的进入路径调整，保存原计划、观察与执行副本。作用结果必须逐字保持，其余事件、参与者、相机和结局不改；缓存同时绑定尾帧哈希与模式，重启不重新规划、不重复提交。精确动作和动作参考不获得此自由。

### 本地定妆素材

正式 `VideoGenerator.generate_all` 会在首次视频执行前读取工作区的 `visual_assets.json`。这是可选的已准备素材入口，没有自动图片生成和新增付费。可先使用 `--plan-only` 获得人物 ID，再放入素材；一旦开始执行便冻结绑定。图片必须位于同工作区 `visual_assets/` 内，支持 PNG/JPEG、至少 64×64、最多 1600 万像素且不超过 10 MiB。示意格式（哈希需填写真实值）：

```json
{
  "version": "visual-assets-v1",
  "characters": [
    {"name": "与分镜一致的人物ID", "path": "visual_assets/character.png", "sha256": "图片文件的64位SHA256"}
  ]
}
```

清单按独立角色绑定；重复身份、相同图片绑给不同人物、越界路径、损坏图片、内容变更和恢复时换绑均停止。`visual_asset_binding.json` 记录 prepared/text_bootstrap 与尚未绑定人物。实际请求按图片顺序明确写入人物 ID；真实尾帧仍只承担状态交接，不冒充独立定妆。明确绑定的定妆图不能在审核或读取失败后被自动移除。当前没有新增上传 UI、场景/道具素材编辑器或自动定妆图生成器；不把这些描述为已实现能力。

## 2026-10-28：连续动作编排，避免回合式武打

用户要的是有身法、节奏、虚实和借势的武侠动作，少量动作也能成立。原时间轴把一切重叠都判错，无法表达闪让尚未结束就开始反击；旧事件也缺少明确的闪避/拨挡语义。只加武功名称或“行云流水”无法解除这种表达限制。

现在交互可声明 `response_kind=impact/evasion/deflection`，区分命中、让开与拨挡；省略仍保留旧命中义务。`flow_from_previous` 描述具体承接的重心、步法、兵器方向或空间变化。只有相邻交互存在共同参与者且声明衔接时，才允许时间搭接；开始、结束与作用时刻保持顺序，不能嵌套、倒序或用重叠重复计算动作时长。首节拍、静态收势不能冒充这种衔接。

正式分镜规划要求以连续动作句安排招式，不强制交替出手、每招命中或每招复位。例如“掠上屋脊的落步接斜劈，对方让锋时转身反手出招，来者借余势压低剑路”可以是连贯运动，而非逐招暂停演示。这里不增加默认事件配额，也不搭建更大的数值建模系统。

正常提示、安全提示、指纹和恢复保留同一份衔接合同。语义验收要求明确的 `flow_continuity_valid`，中间复位/停顿/瞬移或身体动作矛盾即使两招分别完成也不能通过；在衔接边界前后增加采样。闪避要求威胁可读和目标避开，拨挡要求改变来势，均不能以错误命中代替。验收版本 v21 避免复用旧结论。旧未声明字段的合同和提示保持兼容。

离线验证走正式分镜 SDK 接口替身、提示编译、验收及缓存恢复，包含同一人连续出招和非武打的设备交接，证明这不是题材关键词补丁。真实武侠观感与流畅程度仍需原片证据；稀疏采样不证明逐帧动作质量。本轮没有远端模型、上传或付费生成。

## 2026-10-28：状态事务、执行互斥与有界恢复

故障注入证明，原子的文件替换并不等于原子的状态修改：两个从同一工作区恢复的实例都能占用预算 1 的唯一授权，旧实例保存进度还会抹掉已提交账本。现在所有清单修改在同一文件锁内重读、计算、提交，同实例线程再由可重入锁串行化；独占随机临时文件、文件与目录同步保证提交前记录落盘，写入失败保留已落盘状态。显式保存旧快照会拒绝覆盖。正式 `VideoPipeline.run` 在读取恢复输入前取得工作区执行锁，跨 CLI/Web/进程只能有一个执行者；竞争者不能把原运行标为失败，取消或退出释放锁。保护范围是当前本地文件系统上的合作进程，不宣称支持分布式存储锁。

崩溃可能发生在预算占用与镜头提交记录之间。没有确认结果的 `reserved`，或已记录远端 ID 但缺少相应镜头记录的 `submitted`，会阻止再次生成；保留预算等待核对原任务。不能将“没有 ID”推断为“没有收费”。已有完整提交描述的任务继续按原 ID 轮询，正常完成结果仍可复用。

动作准备把可恢复服务故障与无效响应、无效几何、损坏素材区分开。总规划调用上限仍是 **2 次**，包括数值纠正及以后恢复，调用前持久化计数，不自动退还未知结果的次数。连接/超时、限流、认证或服务故障仅在显式恢复时使用剩余额度；无效输出、耗尽额度、未知中断或来源校验失败不重复调用。旧失败记录没有明确分类时保持停止。成功的包继续复用，不自动上传。这不是视频 Take 预算，也不代表文本规划免费。

正式入口把 `motion_control` 传入分镜规划，用户语义中的参考要求不能被文字模式覆盖。创意生成前用共用能力检查核对冻结槽位；当前 v1 无法满足的多镜头、多交互计划提前报错。支持范围与要求同时进入创意提示，具体动作仍需通过原有底层几何/媒体校验，不能通过减少动作或改写结局绕过限制。当前单接触二维预演能力没有扩张为武器、多招或移动相机控制。

回归覆盖跨实例覆盖、多线程/进程抢预算、同一运行竞争/取消、写入失败、锁符号链接、提交中断、有界恢复以及规划前拒绝。SDK 替身隔离远端，媒体部分实际执行 FFmpeg。验证记录与 JUnit 位于 `output/offline-state-recovery-20261028/`；历史原片与账本不变，本轮没有真实模型、上传或付费生成调用。

## 2026-10-28：离线自验发现的后续缺陷

在前轮完整回归通过后，继续通过实际接口做故障注入，发现并修复三类漏检：续拍会把 phase=trigger 的物理交互误当可改写入场；安全重试会丢失非交互时段的状态结果；预演包和提交前检查只证明媒体哈希/规格一致，无法发现哈希已更新的黑屏、静止或倒放。

这是对受控骨架参考的采样渲染验收，不是生成模型的视觉语义验收。阈值是有损编码容差，不能解释为物理正确率或电影质量评分。本轮实际产出 4 秒/96 帧参考并完整解码，22 个采样时刻通过，关键帧图已人工检查。新增 14 项回归；完整 **976 passed**（115.87 秒），`compileall` 和差异检查通过，无远程模型/上传/付费调用。详细故障记录、JUnit 和媒体在 `output/offline-self-acceptance-20261028/`。

## 2026-10-28：共享执行语义修复（当前离线版本）

真实失败片段 `output/20261028_145258_311129` 显示持续架剑，未完成合同要求的推开和失衡。工程事实是：旧结构把一镜压成一个执行者/一次作用，安全提示又限制新动作；固定机位的视觉约束还把主体朝向当成全程不变。此前的时间预算和失败拦截不足以提供多招动作执行。建模也没有接入这个真实运行，它实际只用了文字输入。不能据此断言供应商模型是唯一根因，更不能声称已获得精确动作控制。

修复继续遵循单一 Action Contract owner：v4 计划保留多事件预算，每个交互事件携带执行者、目标、几何、时间窗、作用时刻、反应时刻和可见结果。密集 5 秒槽位默认至少两个事件；可有角色交替。普通提示、安全重试、因果范围校验、逐事件验收共用该投影。相邻镜头继续只接受真实 Observed State，不能把未发生的中间动作补成文字。旧 v3 时间计划仍按旧版本复核，不强行升级历史数据。

这是一项最小公共能力：复用于训练接触、工业搬运、喷涂、区域加热、连杆传动及动作戏；没有新增题材识别表或第二套工作流。主体起始朝向与摄像机固定是不同约束，允许合同内转身。音乐不能重写已经冻结的镜头时长。每个新 Take 的来源与验收状态独立保存，预检或预算失败不制造未提交的 Take，也不覆盖上一条真实任务。

数值预演通过 `prepare_motion_previsualization(storyboard, workspace)` 接入正式 `VideoPipeline`，CLI/Web/恢复保存同一个 `motion_control`。用户明确要求动作参考时先规划数值、校验几何并实际渲染媒体，再核验素材绑定；来源、模型、文件变化停止复用。默认文字运行写明 `text_guided`，不冒充建模。模型输出只是数据，受字段、帧数、文件路径、哈希、资源上限与工作区锁约束；不会执行返回脚本。SDK 替身测试关闭 HTTP，真实 FFmpeg 输出用于证明媒体产出。
